# Reception and patient registration

Reception endpoints are provisional until they are reconciled with Person 3's
API specification. The module uses the existing `patients`, `visits`,
`organizations`, `users`, `roles`, and `audit_log` tables; it does not add or
change schema objects. Patient/visit timestamps use the MySQL server's local
time.

## Access and routing

The reception page and every reception API require an active session whose
database role is `receptionist` or `system_administrator`. State-changing API
requests also require the existing `X-CSRF-Token` header. The responsible
user ID is taken from the authenticated session for visit creation and audit
records, never from request data.

| Method | Route | Access | Purpose |
|---|---|---|---|
| GET | `/api/reception/dashboard` | Receptionist, system administrator | Live counts and recent registrations |
| GET | `/api/reception/organizations` | Receptionist, system administrator | Schools and referring facilities for visit source selection |
| GET | `/api/reception/patients?search=` | Receptionist, system administrator | Search by patient number, national ID, or name |
| POST | `/api/reception/patients` | Receptionist, system administrator + CSRF | Register a patient |
| GET | `/api/reception/patients/{id}` | Receptionist, system administrator | View patient details and recent visits |
| PATCH | `/api/reception/patients/{id}` | Receptionist, system administrator + CSRF | Complete an emergency temporary record |
| POST | `/api/reception/visits` | Receptionist, system administrator + CSRF | Create and route a visit |

Use the existing entry point without URL rewriting:

`http://localhost/hospital-system/backend/index.php?route=%2Fapi%2Freception%2Fpatients`

Patient registration requires `first_name`, `last_name`, `date_of_birth`, and
`gender`; `national_id`, `phone`, and `address` may be blank. Patient numbers
are generated by the API. A repeated national ID is rejected with HTTP 409.
An exact name/date-of-birth match returns HTTP 409 with possible matches; the
client can ask the receptionist to confirm a separate record before retrying.
Set `is_temporary` to `true` for an emergency patient who cannot provide full
details. The API permits missing names and date of birth for that record, and
the record must start an emergency visit. Use `PATCH /api/reception/patients/{id}`
to complete the required details after the patient is stabilized; the patient
number and visit history remain unchanged.

Visit creation requires `patient_id`, boolean `is_emergency`,
boolean `medication_collection_only`, and `visit_source` (`walk_in`,
`school_appointment`, or `referral`). School appointments must select an
organization of type `school`; referrals must select a
`referring_facility`. `source_notes` is optional.

Routing follows the arrival flow:

- Emergency: `emergency_in_progress` (treated before payment).
- Medication collection only: `awaiting_pharmacy` (skips ticket payment and
  nursing assessment).
- All other arrivals, including school appointments and referrals:
  `awaiting_ticket_payment`.

The user must not submit both emergency and medication-only flags together.
Ticket payment and nursing are downstream modules and are not implemented
here.

## XAMPP and Postman checks

1. Start Apache and MySQL, then sign in using a receptionist or administrator
   account.
2. Open `http://localhost/hospital-system/frontend/reception/index.php`.
   The page shows live database counts and the registration/search/visit
   controls.
3. In Postman, first call `GET /api/auth/me` using the browser/session cookie
   to obtain `data.csrf_token`. Keep the same session cookie for API calls.
4. Search with `GET /api/reception/patients?search=...`.
5. Register with `POST /api/reception/patients` and JSON fields matching the
   contract above. Expect HTTP 201 and a generated `patient_number`.
6. Retry the same national ID and expect HTTP 409. Try the same name and date
   of birth and expect a possible-duplicate warning before confirmation.
7. Create visits with `POST /api/reception/visits` and the CSRF header.
   Expect `emergency_in_progress`, `awaiting_pharmacy`, and
   `awaiting_ticket_payment` for emergency, medication-only, and normal
   arrivals respectively. School appointments and referrals also remain
   `awaiting_ticket_payment`.
8. Without a session, expect HTTP 401. With an active account whose role is
   neither `receptionist` nor `system_administrator`, expect HTTP 403.

Example patient request:

```json
{
  "first_name": "Demo",
  "last_name": "Patient",
  "national_id": "DEMO-RECEPTION-001",
  "date_of_birth": "1990-04-12",
  "gender": "unknown",
  "phone": "+1 555 0100",
  "address": "Fictional demo address"
}
```

For an emergency patient whose full details are not yet available:

```json
{
  "first_name": "",
  "last_name": "",
  "date_of_birth": "",
  "gender": "unknown",
  "is_temporary": true
}
```

After stabilization, send `PATCH /api/reception/patients/{id}` with the
required full name, date of birth and gender fields to complete the record.

Example school-appointment visit request (use an organization ID returned by
`GET /api/reception/organizations`):

```json
{
  "patient_id": 1,
  "is_emergency": false,
  "medication_collection_only": false,
  "visit_source": "school_appointment",
  "source_organization_id": 1,
  "source_notes": "Fictional demo appointment"
}
```

This is an academic prototype and is not for real patient data or clinical use.
